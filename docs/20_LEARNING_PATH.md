# 20. Owner Learning Path — SeoulMarketers

## 전제
창업자가 Next.js, Three.js, SQL, 테스트 프레임워크를 아직 리뷰할 수 없다는 것을 가정한다. 설명은 실행 가능한 재현 절차로 구성한다. 개발 품질 책임을 사용자에게 이전하지 않는다.

## 읽는 순서
0. README → `docs/PRODUCT_REQUIREMENTS.md`: 왜 만드는가?
1. `docs/ARCHITECTURE.md`: 프론트엔드/API/DB/배치가 어디에 있는가?
2. `tests/`: 무엇이 정답인가? 테스트가 무엇을 보장하는가?
3. `src/domain/`: 가장 중요한 계산 함수의 입력/출력은?
4. `src/adapters/`: 외부 공공 API 데이터가 어떻게 들어오는가?
5. `src/app/`: 화면에서 어떻게 결과를 보여주는가?
6. `docs/REVIEW_REPORTS/`: 실패→성공 로그와 증거.

## 각 PR 학습 문서에 반드시 포함할 내용
- 3줄 요약, 구현 목적 및 고객 가치
- 읽을 파일 순서(최대 5개)와 파일별 1문단 해설
- 코드 흐름: 사용자 행동 → UI → UseCase → Domain → Repository
- 새로운 개념 3개 이하: 한 문단씩 정의, 이 프로젝트의 코드 라인 링크
- 실행 명령 3개: 테스트, 로컬 실행, 실패를 재현하는 명령
- 변경 전/후와 테스트 실패→성공 증거
- 질문 3개와 풀이(스스로 학습 확인용)
- 한계와 다음 단계

## 학습을 위한 파일 스타일
- public 함수는 입력·출력·단위·예외 계약을 문서화한다.
- 주석은 코드 반복보다 '왜 이 규칙이 존재하는지'를 설명한다.
- 복잡한 비즈니스 계산은 작은 고정 Fixture에서 수기로 검증하는 예제를 첨부한다.
- 테스트 이름은 한국어 문서에서 해석할 수 있게 behavior 중심으로 작성한다.

## 세 가지 입문 용어
Next.js = React 웹페이지 및 서버 렌더링을 돕는 프레임워크.
Three.js = 브라우저에서 3D 장면을 그리는 라이브러리.
PostgreSQL/PostGIS = 구조화 데이터와 위치·도형 관계를 저장/검색하는 DB.

## 학습용 실패 실험
Agent는 제품에 영향을 주지 않는 예제 브랜치에서 '반드시 깨지는 테스트'를 재현할 수 있도록 기록한다. `main`에 의도된 실패를 남기지 않는다. 사용자가 변경을 되돌리기 쉬운 명령을 제공한다.

## 진도 평가
기술 용어 암기가 아닌, '이 함수의 입력이 바뀌면 어떤 테스트가 깨질까?'에 답할 수 있으면 학습 성공이다.
