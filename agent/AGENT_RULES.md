# AGENT RULES — SeoulMarketers

## Mission
3D 상권 시뮬레이션. Three.js 도시로 유입, 상권 데이터·가정 기반 비용 시뮬레이션으로 가치 제공.

## 실행 방식
- 개발자는 Agent. 창업자의 코드 이해 부족을 기술 승인으로 메우지 않는다.
- Agent는 scope 안에서 설계·테스트·구현·CI를 책임지고 증거를 남긴다.
- 사용자에게는 **제품 의사결정**과 실제 화면 피드백을 요청할 수 있다. 아키텍처 정답 판정을 요청하지 않는다.
- 구현 작업은 작은 단위로 진행. 독립 작업 병렬 가능, 종속 작업은 필요 조건 통과 후.
- main 브랜치 직접 무검증 push 금지. PR 기반 테스트 후 merge; 자동 merge 정책은 저장소 설정과 사용자 배포 권한에 따름. 운영 배포/유료기능/외부 결제는 별도 명시적 승인.

## TDD 증명
1. 요구사항 ID+인수조건 정리.
2. RED: 신규 테스트 작성, 해당 테스트가 요구사항에 맞는 이유로 실패함을 로그로 보임.
3. GREEN: 최소 코드로 통과시킴.
4. REFACTOR: 공개 동작을 유지하며 단순화.
5. VERIFY: lint/typecheck/unit/integration/e2e/build, 가능한 것만 '실행 완료' 표시.
6. DOCUMENT: 변경된 DB/로직/API/UX/테스트와 제한사항 업데이트.
7. TEACH: 코드읽기 가이드, 실행 절차, 기대 출력, 개념 해설 추가.
8. EVIDENCE: PR에 커밋 SHA, 명령, exit code, 테스트 개수, 실패/성공 로그 첨부.
9. 남은 위험과 차기 Task 작성.

## 작업 제한
- 단일 작업 범위 변경만 허용. 미정의 요구사항은 문제/가설을 명세하고 안전한 가짜 데이터로 데모를 만들되 DEMO를 명시.
- API 필드는 실제 응답 또는 테스트 Fixture 계약 검증 전 확정하지 않음.
- 외부 데이터 license, 개인정보, 인증, 금전/중개 기능은 별도 compliance gate.
- 유료 기능과 실제 거래·입찰은 미구현 상태를 기본값으로 둔다.
- 통계·추천은 출처, 갱신 시점, 분모, 누락을 보여주며 수익을 보장하거나 강박적 사용을 유도하지 않는다.

## 개발자 품질 정의
가독성·예측가능성·응집도·결합도 4축을 코드 리뷰 기준으로 사용.
읽는 사람이 코드를 이해할 수 있도록 간결한 책임 분리. 추상화는 변경 가능성 또는 반복되는 결합을 줄일 때만 도입.
- Domain은 React/Three.js/HTTP/SQL에 의존하지 않는다.
- UseCase는 Port 인터페이스에 의존한다.
- Adapter가 외부 API/DB를 감싼다.
- Presentation에는 실데이터 집계 계산을 두지 않는다.

## 사용자를 위한 보고 포맷
목표 / 변경 파일 / 코드읽기 순서 / RED 로그 / GREEN 로그 / 실제 시연 / 남은 위험 / 비기술적으로 선택해야 할 사항.
절대 테스트 성공을 추정하지 않는다. 임시 스크린샷과 실측 결과를 구분한다.
